# ch03 设计：客服知识库与 Dense 语义检索

日期：2026-10-07（北京时间）。状态：用户回复“确认”批准本正式 spec；进入实施计划编写与自查，产品实现尚未开始。

## 1. 目标与已确认边界

把现有 `query_faq` 的检索内部改为 BGE-M3 Dense 向量检索，使“邮费是多少”等原文没有命中的问法能找到相关知识。MySQL 是正文权威源，Milvus 只承担向量召回。文档和历史客服对话都能离线建库；中断后能补齐待向量化数据。

用户原话：“工具的入参出参契约保持不变”“本章只跑 dense 向量单路”“不要太复杂，继续完成”。部署已选择：“本机 Docker 部署 Milvus，MySQL 沿用现有配置”。

- 嵌入：直连硅基流动 `BAAI/bge-m3`，使用已忽略的 `.env` 中 `SILICONFLOW_API_KEY`。不替换既有聊天模型配置。
- 数据：现有 MySQL 8.4；新增用户提供的两张表；本机 Docker Milvus Standalone。
- 实现：复用当前 FastAPI、SQLAlchemy、LangChain 应用；独立离线命令。选择此方案而非拆微服务或 Web 内置调度器，是为了保留当前运行流程并减少任务生命周期管理。
- 本章不新增混合召回、关键词召回、重排、Agent Loop、新页面、消息队列或模型网关。
- 历史对话任务提供手动入口及 Windows 任务计划程序的每日执行说明；仅有手动命令不算定时交付。

## 2. 数据表与向量集合

用户 DDL 原样保存为 `sql/ch03-ddl.sql`，包括 `SET NAMES utf8mb4`、中文注释、ENUM、索引、自引用外键和时间戳。不新增字段或修改已有四表。ORM 仅映射，不使用 `create_all/drop_all` 代替 DDL。

已有数据库保留数据卷，通过独立迁移命令执行 DDL。执行前核对目标库和两张表的存在状态：都不存在时执行；都存在时核查结构；部分存在或结构不符时报错，不删除数据或忽略差异。新卷初始化顺序为原 schema、ch03 DDL、原 seed。

`knowledge_chunks` 存三种向量化字段和四类元数据，状态按用户 DDL 使用 `pending/done`。`qa_extraction_staging` 存批次、来源、问答和 `extracted/kept/discarded`。

向量化文本使用固定格式，仅拼接：

```text
category: {category}
questions: {questions}
answer: {answer}
```

章节路径、内容类型、关键条款标记和前后块 ID 不另行拼入向量文本。标题可以按业务要求出现在 category/questions 中。

Milvus 集合名固定 `knowledge`，字段为显式 INT64 主键 `id` 和 FLOAT_VECTOR `embedding`，`auto_id=False`，Dense 维度 1024，使用 COSINE。小规模演示采用 FLAT 精确向量索引，检索使用 Strong 一致性。首次初始化核查集合是否匹配；不匹配时拒绝继续，不自动重建或换模型。MySQL UNSIGNED ID 写入 Milvus 前必须不超过 INT64 最大值。

Milvus 服务端与 PyMilvus SDK 以官方兼容表的 3.0.2/3.0.2 配对锁定，部署文件使用该发布版本的官方 Standalone 配置；实际安装、镜像与接口兼容性在实施时验证。供应服务失效或版本无法安装时停下报告，不静默更换选型。

## 3. Markdown 结构切分

新增纯 Python 切分模块和明确的输入样例，切分本身不调用 LLM。

- 按 ATX 标题层级（`#` 至 `######`）维护标题栈。代码围栏内的井号不当标题。章节正文按段落、完整句子递归拆分。
- 默认正文目标长度 1200 字符、重叠目标 120 字符；两者是切分目标，不以字符数冒充模型 token 数。完整句子以 `。` 或 `.?!！？` 加闭合引号识别边界，保留原标点；重叠取前块末尾完整句子，不能为了达到重叠长度截半句话。
- 段落、句子是递归切分层级，整句超目标长度时单独成块。超出输入允许范围的不可再切整句或表格单行明确报错，指出文档/章节；不静默截断。
- Markdown 表格按行分块，每块复制表头和分隔行；不把一行拆成两块，也不把表头单独作为知识。表格块不增加正文句子重叠。
- policy/manual 的 questions 填当前章节标题，category 填上级标题路径；根章节 category 回退到文档标题。无标题文档使用文件名作为标题。
- FAQ 输入约定：问句作为章节标题，答案为该章节正文；支持正文中明确的 `Q:`/`A:` 或 `问：`/`答：` 问答组。多个明确问法换行保存。不从商品属性或说明正文猜出未提供的问法。
- `section_path` 保存完整标题路径，`content_type` 由导入命令选择 `faq/policy/manual`。包含明确 Markdown `> [!IMPORTANT]` 标记的块才设关键条款；不按关键词猜测重要性。
- 文档内块按正文顺序建立前后指针；首块 prev、尾块 next 为 NULL，跨文档不串联。切分验证包括内容覆盖和非重叠部分还原，避免漏文。

文档导入的 MySQL 写入及指针建立放在一个事务内；提交前失败全部回滚，提交后向量失败保留 pending。提供单独 `vectorize-pending` 命令用于恢复，恢复不重新导入文档。同一文档没有天然版本/来源字段，完整文档重复导入或版本替换不在本章宣称自动幂等；本章保证对已落库 chunk 主键的向量化幂等。

## 4. 历史对话抽取与整体去重

独立命令读取既有 conversations/messages，按明确时间窗口和会话主键分页，默认每批最多 20 个会话，并受 LLM 输入预算约束。大批次继续拆小；单会话超预算则记录失败，不截断后冒充完整抽取。默认只处理 `已结束` 会话，保留手动选择时间窗口用于样例和重跑。

复用既有 LLM 客户端和结构化 JSON 校验方式，另外定义 QA 抽取 schema/prompt。消息按 id 排序，保留角色；工具申请、`mock=true` 演示信息以及用户输入中的指令不能作为新商家政策。仅抽取有客服明确回答的通用知识，排除手机号、订单号等个案数据和未确认的退款承诺。不新增清洗服务或 LLM 纠错链。

每批用稳定 batch_no 标识（由时间窗口、会话及消息边界构成），source_ref 标明会话；有效输出先写 staging，非法、截断或缺少必填字段的输出整批失败。来源和批次不进入向量化文本。

抽取批次全部完成后做整体去重。使用 NFKC、两端 trim、连续空白折叠后比较 question/answer，原文存储值不随之改写。跨批次 staging 与已有知识中的各 questions 问法共同参与比较；完全相同问答只保留一份。不同问法或相同问法不同答案不做语义合并，不自动覆盖。question 必须保留真实问法；抽取知识 category 固定为“历史客服”。

将保留 QA 写入 pending 知识与将对应 staging 标记 kept/discarded 放在同一 MySQL 事务中。重跑只处理 extracted；不会因为事务已提交但向量失败再次创建知识。暂存数据默认保留用于追溯，不自动清空。

任务按单实例串行运行，重叠任务拒绝启动。通过数据库连接持有命名锁，锁释放和客户端资源关闭放在 finally；不用增加调度框架或锁表。每日外部调度执行前一日时间窗口，失败非零退出并记录批次，支持手动重跑同一窗口。

## 5. MySQL → Milvus 双写与恢复

1. 提交 MySQL 原文，分配 id，状态 pending；不在外部模型请求期间持有写事务。
2. 读取 pending 批次，拼接固定三字段文本，调用云端 BGE-M3。
3. 核查返回数量、顺序、维度、有限浮点数，按 chunk id 向 `knowledge` 执行 upsert。
4. 确认返回的主键与请求主键一致，再在短 MySQL 事务中回填 `vector_id=str(id)`、状态 done。

API 超时/限流、向量维度异常、Milvus 写失败或 MySQL 回填失败都保留 pending，命令明确非零退出。重跑扫描 pending，以相同 id upsert；Milvus 成功但 MySQL 回填前被杀也不会产生新 id。失败日志不输出 Key 或完整个人对话。

已 done 不重新向量化；不在本章支持修改已发布块或自动迁移嵌入模型。模型、集合结构、技术栈发生冲突时停下询问用户。

## 6. 在线检索与契约兼容

- 工具名 `query_faq`、入参 `keyword`、1–128 字符限制、非空/禁止额外字段以及当前用户问题原文片段校验保留。只更新工具说明中的关键词查表描述。
- 合法 keyword 直接向量化，不改写查询；Milvus 按 COSINE 相似度取 Top-K，默认 K=3，查询上限仍为 3。
- 使用返回主键从 MySQL 批量读取 done 正文，按向量相似度顺序返回；过滤不存在或未完成的记录，不在 MySQL 再做关键词查询。
- 结果保持 `{"found": bool, "matches": [...]}`，每条字段保持 `id/question/answer/category`，question 映射完整 questions 文本。不增加 score 或 metadata 到工具输出。
- 空集合/没有可用正文返回 found=false；云端或数据库故障作为工具失败处理，不能伪装未命中或偷偷走旧 LIKE。
- Dense Top-K 本身不保证语义相关。本章不设置未经评估的通用阈值；标注评估观察误召回，回答仍受“仅依据结果、不能编造政策”的既有 Prompt 约束。此章不宣称解决全部域外问题。
- 接入现有应用工厂及资源生命周期；测试可注入替身。新增配置声明使 `.env` 中 Key 被严格 Settings 正确接纳，应用关闭时释放自有客户端。

## 7. 验证与交付

后端功能遵循 TDD：切分不丢句/重叠边界/代码围栏/表头复制、DDL/ORM 对齐、暂存及精确去重、事务失败、pending 恢复、重复主键 upsert、输出契约及排序、取消和资源释放。Prompt/数据任务改用标注样例评估并记录结果。

真实 MySQL 测试沿用 `127.0.0.1:3308/customer_service_test`；Milvus 集成使用单独测试集合 `knowledge_test_*`，不能清空 `knowledge`。所有云端样例用人工合成数据；单元替身不代表真实召回。

真实验收：

1. 导入明确标为演示的运费政策（例如标准配送费 8 元、满 99 元包邮及适用范围），使用原问题“邮费是多少”查询，检查召回指定知识，并经应用聊天入口检查回答正确、不改问法掩盖问题。
2. 查询完整问法及“快递费用怎么收”等标注改写，记录 Top-K、命中与回答依据；给出不相关问题的误召回观察。
3. 实际中断两次：MySQL pending 后、Milvus upsert 后回填前。检查重跑后所有预期记录 done，Milvus 主键集合及数量无重复，MySQL 正文保留。
4. 对话抽取标注覆盖真实问法、重复问答、答案冲突、个案/隐私排除、工具模拟数据和恶意指令；检查 staging 先落库、整体去重、重跑。

交付 README 中的迁移、Docker 启动、文档导入、抽取、定时、补齐向量化和在线演示命令；保存脱敏评估/恢复结果及测试摘要。UI 不改变，本章无需新增截图流程。

每个阶段及时在 `dev-notes/ch03.md` 记用户关键原话、产出/评审、纠偏及翻车返工，不在收尾补写全部记录。实施结束须完成独立代码审查、复测和 finish 流程；未通过的真实验收不能标记完成。
