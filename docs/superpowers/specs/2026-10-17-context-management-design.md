## 1. 目标与已确认的范围

让客服在同一会话中持续理解先前的订单、商品及未解决诉求，同时把实际模型输入控制在配置窗口内。原始历史完整保留；压缩只改变模型视图，装得下就不压。会话之间隔离，不做用户画像、跨会话记忆、语义检索历史或按主题重要度挑历史。

保留第六步的确定性路由、订单选择暂停恢复、强制政策检索、证据闸、退款待审核、独立人工/工单交互及既有业务工具。历史和摘要只能帮助理解用户所指；不能替代本轮订单/物流读取，也不能成为退款资格或政策引用的权威依据。第六步已有维修等质量缺口不因本章设计而视为已解决。

## 2. 架构和模块边界

选择应用生命周期拥有的摘要管理器。请求级 `BackgroundTasks` 不负责长会话任务的统一并发、关闭和恢复；另建持久任务队列表又超过本章需要。现有 MySQL 边界和摘要段已经足以判断哪些范围尚未完成，重启可重建任务，不引入新组件。

| 模块 | 职责与输入输出 |
| --- | --- |
| `app/context/tokens.py`、`budget.py` | 统一估算实际消息/工具结构；从窗口、阶段、配置推导预算和启动诊断。纯计算，无 SQL/模型调用。 |
| `app/context/layers.py`、`view.py` | 按完整轮次、两个锚点生成层2/层1/摘要视图；输出不可变 `ContextSnapshot` 和实际调用包，不修改原始消息。 |
| `app/repositories/context.py` | 读取边界/摘要段，推进层1边界，原子追加摘要段及覆盖锚点；每次操作独立短事务。 |
| `app/context/summarizer.py`、`manager.py` | 新批次事实提炼、校验、受控并发、超时/关闭处理；不写活跃图的 `messages`。 |
| `app/context/logging.py` | 专用 `log/app.log` 上下文记录，独立于现有只允许元数据的 Workflow 审计 logger。 |
| 现有 Workflow / Agent | State 保存完整历史；调用前向统一构造器请求模型视图；节点只提交新消息增量。 |
| 现有会话 API / 原生聊天页 | 只读会话列表及原文回载；新会话、切换、摘要标记、引用/动作恢复。 |

请求路径：读取完整历史及边界 → 按预算推进必要的层1边界 → 冻结本轮快照、记录 `history_ctx` → 原有理解/分类/路由/Agent → SQL＋根 checkpoint 完成 → 通知摘要管理器检查阈值。若请求开始时已有超预算层2，也可立即通知；不等待模型生成摘要。

## 3. 数据与边界不变量

沿用用户提供的两步 DDL，形成 `sql/ch07.sql` 与 `sql/ch07-layers.sql`；两个文件都含 `SET NAMES utf8mb4`，按顺序执行。为既有数据库提供检查列存在性的迁移命令，不把重复 ALTER 当成成功，也不自动删除任何列或旧消息。

- `conversations.summary TEXT NULL`：按注入预算选中的最近完整摘要段的文本投影，可重建，不是摘要真源。
- `summary_upto_msg_id BIGINT UNSIGNED NULL`：摘要已处理的覆盖上界。
- `layer1_from_msg_id BIGINT UNSIGNED NULL`：沿用用户 DDL 的**排他边界**，此 ID 之后才是层1。名称不改，文档不解释成包含起点。
- `conversation_summaries` 完整采用用户给的 `id/conversation_id/seq/from_msg_id/upto_msg_id/content/created_at`、唯一 `(conversation_id,seq)` 和索引 `(conversation_id,upto_msg_id)`。一段一行，只追加。

令 `S=summary_upto_msg_id`、`L=layer1_from_msg_id`，NULL 视为尚无覆盖：

| 范围 | 视图 |
| --- | --- |
| `id <= S` | 不再回放逐条消息，由对应摘要段提供背景。 |
| `S < id <= L` | 层2，按规则半压。 |
| `id > L` 且早于本轮 user | 层1，原文。 |
| 本轮 user 及其后续工具往返 | 当前轮，不参与历史降级或后台摘要。 |

锚点只能落在已完成轮次的最终客服 SQL ID，且满足 `S <= L`，单调前进。各范围始终附带 `conversation_id` 条件，不能假定全局消息 ID 连续或属于同一个会话。新段 `from_msg_id` 是上个覆盖点后本会话实际存在的第一条消息，`upto_msg_id` 是本批次最后完成轮次的最终消息。

取消、失败、暂停等流水仍保留。模型视图只回放协议完整的已完成轮次，失败工具可作为“查询失败”保留，不能写成成功事实。被覆盖范围里的未完成残留不提炼为已办成事项；其未解决用户诉求可以保留，并标明尚无完成结果。坏角色/损坏结构必须诊断，不为通过预算伪造工具结果。

## 4. 完整 State、增量与旧检查点

`WorkflowState.messages` 改为 `Annotated[list[BaseMessage], add_messages]`。所有已入库消息统一使用字符串 SQL ID；`tool_call_id` 是独立的调用身份，不能拿它充当消息 ID。请求和工具结果均以 SQL 成功写入后的 ID 提交给图，最终答案同样处理。

新会话首次从 SQL 引入完整原文；已同步会话只提交尚未并入 checkpoint 的新 SQL 消息。`load_order/retrieve_*`、Agent 工具节点、`log_response` 等不得返回 `state.messages + 新消息`。Agent 子图出口只返回本次新增消息，避免父图再次合并整份旧历史。模拟预检可在局部副本上拼接，不写入 reducer。

保留外部动作使用的 `state_version=2`，另加 `context_version=1`、本轮边界/摘要快照标识及预算诊断；不改变旧动作 locator 的含义。正常升级只读旧 completed 根，旧根不会被改写。没有 context_version 的旧会话，在下一次新轮开始、取得会话锁后校对 SQL 顺序和稳定 ID，生成新的兼容根。

若旧根缺少较早 SQL 消息，直接追加会导致乱序：仅这次初始化/修复可用官方 `Overwrite(value=完整SQL原文消息)` 建立规范列表，并明确记录 `context bootstrap`；它不是裁剪，也不删 SQL 原文。常规节点仍只走增量。存在 pending 选单时先走既有恢复/被新问题替代规则，不在暂停中改写原轮。对没有完整原文可恢复的损坏记录报错，不用摘要覆盖原始历史。旧 completed 根上的引用、工单和退款入口仍按原 locator 只读核验。

后台摘要仅更新 MySQL 上下文边界及段表。当前图不被后台任务调用 `update_state`；下一轮把新边界读入 State，因此不会出现两个写者同时修改消息历史。

## 5. 三层视图与完整工具配对

**层1**：每条原始 `content`、role、工具名/参数/结果/关联 ID 全部保留，不删问候、不剥离模拟标记、不改答复、也不再沿用第六步只留下订单/物流的历史投影。所需控制信息放在另一个附件里，不改用户原话。

**层2**：用户正文逐字保留；最终客服正文保留前80个 Unicode 字符，超出加固定“后文已截短”标识；工具申请保持原工具名/参数及调用 ID；大块工具结果变成一行归档标识，保留工具名、成功/失败、原 SQL ID、明确的订单/型号身份及 `mock` 标记。该行由程序从真实字段生成，不由模型总结，也不保留长 FAQ 结果。小结果若不超过160个 Unicode 字符可原样保留；归档行按字段上限构建，不截断订单号或工具调用 ID。所有原文继续在 SQL/checkpoint。

保留每对 `AIMessage(tool_calls)` 和匹配的 `ToolMessage`，只改层2结果的视图正文，不造孤立 tool、不把历史结果搬到当前轮。用户/工具请求/结果/最终答复作为完整轮次调整边界，不能裁到一半。

使用锁定版本 `trim_messages(strategy="last", allow_partial=False, ...)` 选择预算内的最近消息候选，再用现有完整轮次校验把边界对齐；它只帮助确定保留哪些完整轮次，不把返回的短列表写入 State。最终必须用同一计数器重新计费，校验层1正文完全相同及工具配对完整，不能仅凭该函数名字认为工具链天然安全。

层1实际用量超 `H1` 才把最旧的完整轮次降到层2，推进 `L`，直到满足；日志给出降级前后用量和边界。层2半压后超 `H2` 才触发摘要。层2阈值是异步触发线，不是同步删除线：摘要未完成时仍保留尚未摘要的内容，只要层1＋层2没有超过本轮历史硬上限。必要时借用未用完的另一层额度，不借输出/安全余量。若后台持续失败或单条超大原文导致必需上下文装不下，显式返回上下文容量错误，不静默丢用户话、不同步等摘要、不把这当知识不足入池。正常两组验收不允许依靠这类错误凑满轮数。

## 6. 统一调用包与前缀顺序

所有历史消费节点使用同一份冻结的 `ContextSnapshot`，包含边界、摘要段及来源范围、层2/层1消息和 token 估算。理解器和分类器共享其历史投影；分类仍只判断当前诉求，输出 `intent/confidence`，不是重新回答历史。固定闲聊也构造并记录快照，但不调用分类或理解模型。

主力 Agent 调用顺序固定为：

1. 本阶段固定 system（人设、红线、协议；只放稳定指令）及固定工具定义。
2. 层2半压消息，时间顺序。
3. 层1原始消息，时间顺序。
4. 当前用户原话。
5. 一条 user 侧结构附件，合并摘要全文、当前检索证据、resolved_question、当前意图/模式、订单引用及售后控制事实；各部分有明确数据边界与来源标签。完整当前订单结果只放在下面的原生工具对，不在附件再复制一份。
6. 当前 ReAct 已发生的原生工具申请/结果对，按调用顺序。

摘要和证据不额外占 system。附件不是用户的新诉求或可执行指令；摘要不是新政策。理解/分类阶段没有当前检索证据，使用相同位置的摘要附件，不能为了凑 role 次序伪造客服气泡。实际 provider 序列化可能合并相邻 user，验收核对最终请求体仍保持上述先后关系。

现有 `agent_decision_system/agent_final_system` 的动态意图、模式、售后理由移入附件；相应所有条件分支写进固定阶段指令。Agent 决策阶段固定暴露既有四个只读工具和一个内部控制 schema，字段固定为 `reply_mode/suggested_actions/refund_decision/decision_reason`；普通路由后二者必须 null，售后路由按原四字段语义校验。统一修改普通和售后解析器，不同时保留互相矛盾的两字段提示词。模型仍是原生工具 auto＋JSON 模式，不引入未经核对的 schema 联合类型。

固定工具 schema 不等于增加权限：服务端仍禁止知识/售后轮重复调用 FAQ，禁止所有写工具进入 Agent；越权选择在执行前拒绝，不能实际重查或提交业务。工具定义按稳定名称排序，不能夹入 conversation_id 等动态描述。决策、最终生成、理解、分类各自有固定前缀；不要求不同任务共用同一段指令。最终生成不绑定业务工具，符合既有只输出正文协议。验收比对同阶段 system＋tools 的序列化哈希跨轮相同，不宣称供应商一定命中缓存。

当前 FAQ 的完整编号证据集中放在附件，不在多个 tool 结果里重复大段拼装。相应当前 FAQ ToolMessage 只保留成功/失败、已合并标识和原调用 ID；当前业务结果按经类型校验的展示副本提供，不能截掉状态、金额、关键时间、错误或模拟属性。SQL/checkpoint 仍保存原始返回。

证据按整 chunk、真实重排分排序选入 `RERANK_TOP_K` 与证据额度；先确定编号再首尾排列，保持第4章引用关系。整块放不下就少选并记录，充分性闸检查**实际选入的那批**，不是检查较大集合再只喂残缺片段。历史 `[n]` 不变为当前 `[n]`。

## 7. token 口径和预算

### 7.1 同一计数器

旧函数按 UTF-8 字节计数（一个常见汉字约3个单位），不能把它的8000当模型 token。新计数器统一覆盖正文、role/边界、tool schema、工具参数、调用关联 ID 和实际 JSON 附件，输出字段名明确为估算 token；费用账本中的 provider usage 仍是实测值，不覆盖为估算。

不假装 OpenAI tokenizer 等于 GLM tokenizer。按中文字符、ASCII/JSON片段和固定协议开销分别估算，用已授权少量实际调用的 `prompt_tokens` 校准，保存样例、版本、误差及安全系数。所有理解/分类/Agent/充分性/摘要入口连同预算一起换用同一口径，不在其中一个入口继续按字节扣账。纯文本早期模式和离线评估保留独立配置，不能误改其业务阈值。未知分词规则留在保守余量中。

### 7.2 配置与计算

本章新增/接通配置：`MODEL_CONTEXT_WINDOW`、`MAX_USER_INPUT_TOKENS`、`MAX_AGENT_STEPS`、`TOOL_RESULT_MAX_TOKENS`、`RERANK_TOP_K`、`CONTEXT_TARGET_ROUNDS`。建议应用默认配置为128000、2000、4、1200、10、40；最终输出继续读取原 `MAX_OUTPUT_TOKENS`（默认512），控制输出使用现有独立上限。`MAX_AGENT_STEPS` 表示最多业务工具执行次数，最后一次收敛决策和最终生成另外预留；与旧 `AGENT_MAX_TOOL_CALLS` 同时配置而不一致时启动报错，不偷偷选一个。

128000 是拟采用的**应用声明预算**，不是已证实的 glm-5.3-flash 供应商窗口。当前官方搜索未取得该精确型号规格；部署者必须让声明值不超过其服务实际支持值。文档和报告不得把一次短请求成功写成128K上限已验证，亦不因此换模型。

每个阶段计算，并取同一轮需要的最紧约束作为共享历史额度：

```text
W = 配置的模型上下文窗口
F = 该阶段固定 system + 真实绑定工具/控制 schema 的估算成本
U = 当前用户输入预留（MAX_USER_INPUT_TOKENS，另计包装）
E = 当前编号证据额度上界（按 Top-K、完整 chunk、实际序列化计费）
G = 注入摘要额度上界
V = 其他动态控制附件上界（resolved_question、模式、理由及来源引用等）
O = 该阶段的真实输出预留（final/control/intent 等分别读取配置）
M = 安全余量
P = 本轮当前 ReAct 工具请求/结果的最大瞬时累计成本
A = W - F - U - E - G - V - O - M - P
D = CONTEXT_TARGET_ROUNDS × 每轮稳态估算成本
H = min(D, 各历史消费阶段的 A)
H1 = floor(H × 0.70)
H2 = H - H1
```

`E` 上界取 `min(6000, ceil(W/8))`，不是改写 chunk；`G` 取 `min(2000, ceil(W/32))`；`M=max(256,ceil(W×0.03))`。这是应用分配规则，不是供应商常量。`P` 按最大工具步数乘每次模型可见结果上限、schema 定义允许的最大参数及调用包装成本；FAQ 正文已在 E，只计其工具回执，不在 P 再算全文。`V` 按控制字段实际长度上限和 JSON 包装计算，不再把该附件漏在公式外；单一订单结果只在 P 中预留，若实际载荷确有重复字段，两个位置均按真实序列化计费。`D` 的稳态用量从一组固定的完整单工具业务轮次样例同口径计算，样例随验收保存，不拿问候字数冒充正常业务。每项及公式版本写 `context_budget` 日志。

历史硬上限之外，每次发出前还校验 `实际完整输入估算 + 本次输出预留 + M <= W`，业务结果超单次上限时不能截半个 JSON 或藏掉关键字段；应停止继续申请、使用已足够且完整的数据作答，仍不足则明确错误/澄清。层1和当前用户不会被偷偷剪短。真实输入超过 MAX_USER_INPUT_TOKENS 在发起模型调用前拒绝；配置额度不承诺任意极大工具结果都能容纳。当前 API 文本长度、理解器 query 字符上限和 JSON 输出预算也须联合核对：合法输入不能因旧512字符上限被理解器截短；若无法在控制输出预算中完整表示，应在调用前给出明确输入限制，不让模型生成半截 JSON。

启动检查 F、参数上限和输出配额可计算、A/H 为正、层1至少装得下固定样例中的一轮完整业务对话。失败记录具体扣项并使聊天功能报“上下文预算不足”，不能截掉 system 或把滑窗设0后假装可用。启动不付费调模型。

`TOOL_INPUT_TOKEN_BUDGET=8000` 不再作为 Workflow 的第二道旧字节上限；旧纯聊天入口可保留其配置。现有 `AGENT_TOTAL_TOKEN_BUDGET=32000` 是**一轮多次调用累计费用保护**，与单次上下文窗口不同。缺省费用保护上限改由图中各阶段最大调用次数和输入/输出预留推导；显式旧32000仍可限制花费，不能悄悄提高。若其无法容纳目标历史下的一次最短合法执行，启动诊断指出冲突，验收启动配置显式采用本章推导值。不通过删历史来绕过费用保护。

### 7.3 演示与长会话上限

演示仍使用用户六项参数：18000/2000/2000/3/1200/5。其他扣项由本仓库的真实指令/schema/证据规则计算。报告同时写明实际 H/H1/H2、计数器版本及每个扣项；不保证最初示例5650。默认与演示测试使用同一业务轨迹，分别载入默认配置和这组六项演示配置，不能把输出、工具步数及 Top-K 的差异说成只改了窗口。

摘要段在库中全部保留；注入时若总量不超 G 则全部使用，超出时只按时间选择最近的完整段，不截半段、不重写早期段、不做语义检索或重要度选择；日志列出未注入的段和覆盖范围。`conversations.summary` 只是这一投影的缓存。多次摘要后的“永远记得所有早期事实”不在有限窗口的保证范围内；本章两组二十轮验收中最初订单所在摘要必须仍被实际注入，否则早期回忆验收失败。

## 8. 后台追加摘要的生命周期

管理器由现有 FastAPI lifespan 创建，默认全应用最多2个摘要调用并发，同一会话最多1个任务，等待队列最多8个会话。满载记录 skipped/busy，之后聊天轮次再次检查，不阻塞聊天等待排队。单次摘要沿用 LLM_TIMEOUT_SECONDS 超时，输出预留512且纳入自己的窗口预算；零上游自动重试。每个任务使用独立 SQLAlchemy AsyncSession，绝不共享请求 session 或聊天事务。

1. 层2超 H2，取得待覆盖范围 `(S,L]`、现有段序号、原文范围摘要哈希。冻结这次目标 L，不追逐后续新消息。
2. `summary trigger/start` 记录阈值、范围、任务 ID、时间。读取该范围原始用户/客服和完整工具流水，不拿层2截断文本当摘要原料，不喂旧摘要回炉。
3. 若原文批次超过摘要调用窗口，按完整轮次切成可装下的连续前缀，逐段生成，直到覆盖这次目标 L。单个超大轮次无法合法容纳则失败并保留锚点，不能偷删事实。
4. 以严格结构响应得到文本，校验正常结束、长度、可追溯实体及否定/动作状态。新摘要不携带引用号作为当前政策证据。失败不落成功段、不推进 S；不自动付费重试同一生成。
5. 用独立短事务锁定 conversation 行，核对预期 S、最后 seq、实际所属范围和当前 `L >= target`；追加唯一 seq 段、推进 S，并更新 summary 投影，原子提交。发生竞争则 skipped/conflict，不能覆盖其他任务的新段。不在模型请求期间持锁。
6. 当前轮使用原快照走完；下一轮重新读段和锚点，不叠加“旧原文＋覆盖它的新摘要”。

段落只提取事实、订单/型号/用户报过的手机号、用户明确诉求、否定和未解决问题。历史状态必须标明是当时读取结果，mock 保持模拟；“想退/打开表单/取消表单”不变成“已退款”。目标50–200个中文字符，实体较多时拆成多个连续批次，而不是丢关键事实去凑长度。纯寒暄批次可产生空 content，仍以一行记录覆盖区间，避免反复触发；不生成“用户很满意”等虚构事实。

关闭先停止接收新摘要任务，给已运行任务最多5秒收尾，再取消并等待清理；关闭模型/SQL/日志资源在其后。未提交段不推进覆盖边界。进程重启仅扫描已发生降级且 `L > S` 的本章会话，不为未降级的旧会话批量生成摘要；分页计算层2是否仍超阈值，任务走同一并发与队列限制，剩余范围可在该会话下次聊天时再检查。启动扫描只做数据库计算，不等待上游摘要；不需要持久任务表，也不宣称进程崩溃中途执行过的上游调用“恰好一次”。同一生成已提交后再次扫描不会重压该范围。

## 9. 摘要与理解的来源约束

摘要保留身份不代表业务状态仍有效。本轮“最开始那个订单后来怎么说”可以由摘要恢复订单号及当时诉求，然后走当前路由重新读取业务结果；没有明确后续结果就承认尚未解决。模型不能因摘要写了“曾问退货”而跳过订单/政策闸。

理解器的实体校验增加摘要 provenance：只允许引入实际注入段内、且可从该段原始覆盖范围追溯到用户明确表达或成功配对工具结果的订单/型号。按段序号和 SQL 范围核验，不做语义检索，不把未注入的全库历史暗塞给理解器。当前明确订单/否定优先；多个未区分订单仍澄清/选单。“最开始/上一单”等位置约束必须对应已注入来源，不能按最近订单一概覆盖。

纯 prompt 的摘要和理解改动使用带标注样例验证；校验器不能证明任意自然语言绝不幻觉，因此报告同时给出原文、摘要、预期事实及实际判定，不把实体正则通过称作忠实度保证。

## 10. 可观测性

新增专用 UTF-8 文件日志 `log/app.log`，路径锚定项目根，不进静态目录或 Git。保持现有 Workflow 元数据审计白名单，另建 context logger 记录内容。实际上下文日志不写运行时 API 密钥、Authorization 头或客户端对象。

| 事件 | 必须字段 |
| --- | --- |
| `context_budget` | 配置、各阶段 F/U/E/G/V/O/M/P/A/D/H/H1/H2、样例/估算器版本、旧累计预算冲突。 |
| `history_ctx` | conversation_id/user_message_id、snapshot_id、S/L、注入段及全文、层2/层1逐条 role/id/content/tool关联、消息数及估算；每轮必打，固定回复标 `sent=false`。理解/分类如实际包不同，各自记录实际消费者。 |
| `model_ctx` | 同一身份、Agent 阶段和调用序号、实际 system/messages/tools/控制附件、摘要及证据、各层条数/用量、输入估算、输出预留、前缀哈希；每次 Agent 调用前写。 |
| `summary trigger/start/done/skipped/failed` | 任务 ID、段序号、from/upto、预期 S/L、阈值/用量、终态原因、开始/结束/耗时。 |
| `context downgrade/bootstrap/error` | 原/新边界、降级用量、完整轮次范围、同步或容量错误原因。 |

这里“原样”指记录真正交给客户端的消息和工具载荷，不只打印摘要字符数、截断预览或一串 ID。采用一条可解析 JSON 记录承载多行原文，`Select-String 'model_ctx|history_ctx' log/app.log` 可定位，再按请求 ID 展开。为理解/分类、扩写、充分性和摘要调用补齐对应阶段的实际调用记录；不把 `sent=false` 快照写成已调用模型。通过捕获测试请求体，比较日志序列化内容与实际出站内容；对调用失败/取消同样保留之前已发送的上下文和成本记录。

## 11. 只读接口和聊天侧栏

继续使用当前演示用户 `demo-user`，两条 GET 由服务端当前演示身份限定 `user_id`。不接受任意用户参数来枚举他人会话，跨用户 ID 返回404。本章不新建登录系统，也不把这一演示身份称为正式鉴权。

- `GET /api/conversations?before_id=...&limit=50`：倒序返回 `id/status/created_at/updated_at/first_question_preview/has_summary` 和 `next_before_id`，ID 均为字符串。首问来自第一条用户原文，没有则“新对话”。按创建 ID 新在前，摘要生成不能把旧会话挤到最前。前端可继续加载所有页，不能只展示最近50条就称为全部。
- `GET /api/conversations/{id}/messages?after_id=...&limit=200&upto_id=...`：第一页冻结 `upto_id`，后续分页完整回载到这一上界；返回原始 role/content/tool_calls/tool_call_id 和字符串 SQL ID，并附最终客服消息对应的引用、工具徽章、动作 locator 等展示元数据。GET 不触发模型、摘要任务或业务写入。

引用、动作从**原轮 durable completed 根**按 `final_message_id` 关联，不用最新根的引用覆盖旧答案，不重新检索一遍冒充当时证据。单次读取可建立内存映射避免逐条全扫描。旧根缺失时原文字面仍显示，缺少来源的角标不伪造可点证据，动作不凭正文重新授予。原始工具流水在接口保留，页面以原用户/最终答复为气泡、工具往返为徽章；失败/未完成轮次明确标识，不制造“这次没有收到完整回复”的历史最终答案入库。

侧栏复用现有主题、移动端收起布局，包含新对话、首问预览、时间/当前项和“已摘要”标记。点击后加载全部原文页，成功再切换当前会话并继续聊天；切换请求使用 AbortController 或请求代号防旧响应覆盖新会话。流式响应/选单提交期间禁用切换，沿用当前防并发行为，不让旧 SSE 写进新会话。新对话只 POST 新会话，旧会话不清空、不结束。

回载后引用仍可打开原 chunk；退款、选单及工单按钮按已有只读核验接口恢复可用性，不重新执行。转人工仍是独立通知＋客服小猫新气泡，工单/退款仍由用户填主题弹窗；原有前端本地反馈不转成后端写业务的信号。侧栏列表或摘要标记加载失败静默降级，输入框照常可用；历史切换失败保留原会话内容，不显示空白冒充成功。

## 12. 验证与交付边界

实现计划将拆成可独立验证的预算/数据层、视图与 reducer、异步摘要、Workflow 接线、只读接口、前端及验收任务，每任务完成即追记 `dev-notes/ch07.md`。产品代码先写有意义的失败测试再实现；纯摘要/理解提示词改动先定义带事实标注的样例，再跑验证。本设计不是测试通过报告。

| 组别 | 必须证明 |
| --- | --- |
| 预算与原文 | 中文/JSON/tool schema 统一计费、窗口/输出/峰值扣项、两配置启动自检、累计账本区分、层1原文全等、边界不拆工具轮次、全局 ID 间隙。 |
| 持久化/升级 | add_messages 无重复/乱序，父子图只发增量；旧完整根/缺历史根/暂停选单/取消后新轮；不删 SQL 原文；动作原 locator 可核验。 |
| 异步与竞争 | 假模型用事件闸挂起摘要，当前回复仍能完成；每会话单任务、应用有界、独立 session、CAS冲突、失败/取消不推进、提交后重启不重压、旧段字节不变。 |
| 标注摘要/理解 | 订单/型号/手机号、否定、多订单、未解决问题、模拟状态、表单打开/取消；不补未出现事实、不丢实体；早期来源确实进摘要再用于理解，不能从未注入历史偷读答案。 |
| API/浏览器 | 同用户全部会话分页、越权404、原文历史＋旧引用恢复、多会话继续、切换竞态、列表失败不中断聊天、主题一致。 |

默认与演示各固定**至少21轮**同一业务轨迹，真实模拟订单读取、政策问答和少量正常澄清混合；第1轮明确订单1001和未解决诉求，中间不反复提醒该订单，最后追问“最开始那个订单后来怎么说”。不能只连发问候绕过所有模型和工具，也不能只增大回复长度、手动改锚点或预置摘要以制造级联。

- 默认：记录实际窗口和累计预算，21轮均完成；S/L 未推进、段表无新增；不发生降级或摘要。
- 演示：使用给定六配置，真实用量触发层1降级、层2超阈值、后台新段；至少一段确实覆盖最初订单所在轮次，最后的 history_ctx/model_ctx 显示该摘要被注入，理解恢复正确订单/诉求并重新读取当前业务结果。
- 两组都核对 SQL 全部原文字节、checkpoint 完整历史、各次真实模型输入未超预算及响应终态。重启后切回旧会话继续聊；原始来源角标可点。用事件/时间证据证明异步，不用“耗时看起来短”推断未阻塞。

先做离线21轮回放与受控模型并发测试，再做少量页面冒烟，最后运行真实两组固定场景。用户持续授权少量 GLM/BGE 页面调用，但不希望上百次大量调用；42轮可能产生超过100次上游请求。实施计划先列出预计和硬上限，运行前核对现有授权，超出范围须取得该固定批次授权，不能因“42轮”就隐藏多次内部调用。失败如实保留，不通过反复重跑覆盖旧结果；定点修复后分别报告单例复验及整组是否重跑。

验收服务拟使用独立端口8004及独立 SQLite 路径，当前8003不覆盖。最终交付可执行迁移/启动/两组演示命令、测试与调用次数、预算计算、日志/SQL/截图证据、`dev-notes/ch07.md`。必须完成实际验收才称功能完成；当前阶段只交付设计。合并、远程推送在用户后续明确要求时执行。

## 13. 接口核对与设计自审
