# 第六步设计：正式分流、指代消解与退款售后子流程

日期：2026-10-15。基线：master `b2d9ed1`。状态：口头方案已确认，书面设计待用户审阅；尚未进入实施计划或产品实现。

## 1. 目标与已确认边界

把第五步的占位分流器升级为结合本会话历史的正式入口。系统先理解用户这一轮想办理什么，再由确定性 Workflow 决定如何获取事实；模型不能猜订单号、跳过政策检索或代用户提交退款申请。

用户原始要求包括：指代消解与口语归一合并处理；核心退款/售后请求在检索侧扩写多条查询；意图只输出 `intent/confidence`，保留“其他”；缺订单时点卡片续办；退款原因在表单中自选。前端继续按用户指定的 Vibe Coding 方式迭代，后端、Prompt 和数据分别走代码验证及标注样例验证。

已经确认的选择：

- 使用 LangGraph 原生 `interrupt` / `Command(resume=...)`，沿用官方 AsyncSqliteSaver 和现有 SSE。
- 纯政策 FAQ 直接检索，不选订单、不扩写。涉及某一单的退款判断、办理诉求及具体售后请求，先查订单再扩写、检索政策。
- 退款表单提交后保存到现有 MySQL，状态为“待审核”，不执行实际退款。
- 默认模型沿用当前 `glm-5.3-flash`，以标注样例验证能力；本章不擅自换模型，不启用大小模型升级链。
- Context7 查询已耗尽月度额度。用户允许本章后续使用官方文档核对，并保留来源、锁定版本和本机接口记录。

不新增数据库服务、模型供应商或检索基础设施，不升级依赖版本。不做跨会话记忆、分类模型训练、审批后台、真实支付、真实订单系统对接或第四步 300 题全量重跑。第五步投诉的独立人工/工单按钮、主题弹窗、引用、反馈及日志能力继续保留。

当前订单与物流本来就是模拟数据。本章把所需订单信息变为可重复查证的演示事实，不将它描述为已接入商家生产业务；现有前端演示身份也不等同于真实登录鉴权。

## 3. 输入理解与意图协议

### 3.1 指代消解与改写合并一次调用

明确的整句问候、感谢和告别保留第五步规则快路，整轮零模型调用。“你好，订单 1001 到哪了”不能命中该快路。其余问题先进入理解节点，再分类。

理解节点读取本会话已完成轮次及其中可信工具结果，沿用现有历史预算和裁剪规则；不引入历史摘要或跨会话记忆。当前用户原话单独保存，已放弃或未完成轮次不作为已确认订单事实。

模型只输出 `{"query":"独立完整问题"}`，额外字段、空字符串、超长文本、工具调用和异常结束均不接受。单条规范问题最多 512 字符，与检索入口一致。已经完整且表达明确的问题要求原样输出；只有口语归一或确有明确先行词时才改写。

约束示例：

- 前轮查过“订单 1001 的 MH-LP200”，本轮“它能退吗”可补为“订单 1001 的 MH-LP200 能退货吗”。
- 前轮只有商品型号，没有订单号，不能凭此添出一个订单号。
- 同时出现两笔订单且“它”无唯一先行词，保留歧义，不凭最近列表位置选订单；具体退款路径展示选择器。
- 当前轮明确说“改查订单 1002”，不能保留上一单 1001；否定、型号、金额、时间和办理动作不得被改写丢失或反转。

服务端检查新增的订单号等关键实体确实来自本轮原话或本会话可信上下文；不在来源中的实体使本次理解失败，不带着猜测继续执行。保存 `raw_question`、`resolved_question` 和改写是否发生，后续检索、分类及 Agent 使用规范问题，低置信度池仍记录用户原话。

### 3.2 八选一分类

模型原始 JSON 必须且只能包含以下两个字段：

```json
{"intent":"退款退货","confidence":0.93}
```

`intent` 枚举为“物流、订单、商品咨询、退款退货、售后、投诉、闲聊、其他”；`confidence` 是有限的 JSON 数值，范围 0～1，拒绝字符串、布尔值和非有限数。严格校验原始文本与结构化解析结果一致，并检查结束状态；`json_mode` 本身不代替业务 Schema 校验。

Prompt 按用户四件套组织：枚举选项、唯一 JSON 协议、边界 few-shot、拿不准归“其他”。分类只决定办理动作，不输出订单槽位、退款原因、节点名称或检索查询。

初始低置信度阈值为 0.70：合法输出低于阈值时，代码将有效意图置为“其他”，同时保存模型原始标签和 confidence。阈值是初始工程规则，confidence 不是已经校准的准确率。协议非法、上游故障或截断走服务错误，不能伪装为“其他”。

| 问法与边界 few-shot | 有效分类与行为 |
| --- | --- |
| “退换货政策是怎样的”“保修多久”“饮水机如何清洗” | 商品咨询；通用政策/说明 FAQ |
| “订单 1001 能退吗”“这个我不要了，申请退货” | 退款退货；缺订单号也不能改判其他 |
| “新买的饮水机不出水”“这台设备需要寄修” | 售后；不转换成退款申请 |
| “订单 1001 物流到哪了” / “我买了什么” | 物流 / 订单，保留业务查询路径 |
| “我要投诉，你们太差了” | 投诉；固定安抚与两个独立选项 |
| “怎么又坏了，帮我修一下” | 售后；情绪词本身不等于投诉 |
| “今天心情不错” | 闲聊；分类后返回固定话术 |
| “蓝色星期八能替我给月亮签收吗” | 其他；友好说明可办理范围并请求明确诉求 |

包含明确投诉诉求时优先投诉；普通多意图请求按当前最明确的办理诉求分类，其余由 Agent 澄清。本章不并行拆成多条业务工作流。库外商品知识仍可归商品咨询并由证据闸拒答，“其他”不能被当成知识库未命中的别名。

## 4. 确定性路由与退款售后子流程

共同入口是 `START → resolve_reference → classify_intent`。固定映射写在代码里，模型不能返回路由目标。

| 有效意图 | 固定路径 |
| --- | --- |
| 商品咨询 | 单查询检索 → 证据闸 → Agent / 资料不足回复 |
| 退款退货、售后 | 解析可信订单 → 必要时暂停选单 → 查单 → 扩写 → 政策检索 → 证据闸 → Agent / 资料不足回复 |
| 物流、订单 | 主力 Agent 自行调用现有读取工具 |
| 投诉 | 固定安抚 + 转人工/建工单建议，不进入 Agent |
| 闲聊 | 固定客服引导话术；规则快路无需理解和分类调用 |
| 其他 | 固定范围说明及澄清提示，不查单、不检索、不自动执行动作 |

所有完成路径汇入日志和 SQL 最终答复保存；等待选单路径暂停，不冒充完成答复。

### 4.1 订单事实先于政策检索

执行阶段从已验证规范问题、原话和明确历史关系提取订单标识；仅接受可追溯且唯一的标识。没有、多个或无法确定指向时展示订单卡片。即使列表只有一单，也由用户点选，不自动替用户选择。

明确但查不到或不属于当前演示身份的订单不能生成模拟成功结果；展示“未找到可办理订单”并允许从当前可用列表选择。候选为空则给出明确提示，不进入政策资格判断。

选择器及 `query_order` 共用一个订单提供器。首批固定演示样本至少覆盖：已签收七天内、超过无理由期限但仍可能在保修期、未发货、退货例外商品。订单含稳定 order_id、所属演示身份、商品名称/型号/品类、状态、支付金额（分）、签收时间或空值、`mock=true` 和业务基准时间。

演示数据采用固定业务时间 `2026-10-15`，时间与“签收后第几天”一并展示为演示口径；不可拿系统今天与固定旧样本混算。卡片、查单工具、恢复后的判断和表单都使用同一版本数据。每轮将选中的订单快照与业务时间写入检查点，暂停后重启不会重新随机生成另一笔事实。物流仍保留演示标记，涉及同一订单的身份及商品信息保持一致。

订单缺少的真实条件，例如商品是否完好、是否影响二次销售，仍是未知，不能由模型补造。超出七天无理由期限也不等于所有质量售后资格一并消失。

### 4.2 扩写及真正的多查询检索

仅在具体退款退货/售后子流程中调用扩写器，且必须在取得订单后。模型输出字段恰为 `queries`，无解释、无槽位或决定字段：

```json
{"queries":["订单1001的MH-LP200能退货吗","电子商品七天无理由退货及运费规则","电子商品质量问题与保修政策"]}
```

该例表示检索视角，不表示已认定订单有质量问题。实际查询按原诉求选择：维修请求扩写故障、保修及寄修；退款请求扩写适用条件、例外及相关运费。保留规范问题为首条，共 2～3 条不同查询，每条最多 512 字符，去空白重复后仍需满足数量；不增加用户未声称的故障、原因或支付事实。格式不合法直接返回可识别错误，不静默采用另一套扩写协议。

每条查询独立执行现有 Milvus dense Top-50 + BM25 Top-50，再由 `hybrid_search` + RRF 融合。跨查询按排名作第二层 RRF（常数 60），以 chunk_id 去重，最多保留 50 个候选；从权威仓储核对可用正文及已校验的品类过滤。随后仅调用一次 `bge-reranker-v2-m3`，以规范问题对合并候选重排到 Top-10。稳定同分顺序按 chunk_id，记录每条证据命中的查询索引。

这要求检索层提供可复用的候选召回入口，不能只拼接几个词成为一条 BM25 查询，也不能各取重排后的十条冒充完整候选。最多三路，初版顺序召回，不新增并行模型执行或无限扇出。全部查询共用本段现有 FAQ 总时限，不按查询条数翻倍；一条上游失败即本次检索失败，不把缺路结果伪装成证据充分。

纯 FAQ 使用规范问题进行一次检索，显式传可信 QueryPlan，避免再调用第四步旧理解器；本章不改评估器既有四策略定义及旧 QueryPlanner 降级语义。知识入库内容与 chunk 数量不因扩写改变。品类过滤作用于每条查询，去重后再次核对，不能合并时跨品类泄漏。

### 4.3 闸与 Agent

知识路径继续使用现有真实 rerank 分数门槛及内容充分性自评，在任何最终答案 delta 前执行。自评以规范问题和当前订单上下文检查政策是否够用；订单事实不能代替政策证据。RRF/BM25 分数不能直接套重排阈值。

证据不足：不进入 Agent，固定说明资料不足，按现有规则把原话和原因写入低置信度池。缺订单、意图不明及上游超时分别处理，不写成知识不足。

强制查单与聚合政策检索分别保存服务器生成、成对的工具申请和结果，日志 `origin=workflow`；向 Agent 提供本轮可信订单事实及实际装入 Prompt 的政策证据。Agent 无需重查已获取的同一订单或同一政策，可继续有限步澄清。工具调用仍累计计数，强制查单与聚合检索合计两次，占用原四次上限；每条内部检索查询不伪装成一次 Agent 自选工具调用。

保持现有 `query_faq` 对模型参数的原话片段约束。Workflow 通过服务器侧入口传递已经验证的规范问题和查询集合，不让模型借改写绕过工具权限，也不把“查询原话”审计改写成模型自选结果。引用重新按最终实际证据全集统一编号，章节路径与原文快照对应，提示词继续首尾放置相关证据。

Agent 不追问退款原因，不猜订单号；确实需要其他条件时可以澄清，或者明确说明待核验。本章不会把“需要寄修/不会使用”强制变成退货判断。

## 5. 原生暂停恢复、状态与并发

### 5.1 状态扩展

沿用现有 ConversationState/WorkflowState 和 SQLite，增加可序列化字段：

- `state_version=2`、原始 SQL user_message_id（即本轮 turn_id），理解来源及 intent/confidence/raw_intent。
- `order_selection`：服务器生成的 selection_id、候选订单快照、业务时间、选中结果；不得保存客户端或数据库会话对象。
- `order_snapshot`、`retrieval_queries`、候选来源和 Agent 退款判断。
- `turn_status` 增加 `awaiting_order`、`superseded`；保留 running/completed/failed/cancelled。
- 分阶段调用次数、usage、计时；人等待时间与服务执行时间分别记录。

旧的已完成检查点允许缺少新增字段，按旧版只读解释；不能因为新字段默认值给旧答复补出退款权限。历史工单建议仍按原不可变完成检查点校验。旧未完成状态没有合法 selection_id 时不能通过新恢复接口伪造续办。

### 5.2 暂停与同轮恢复

1. `prepare_order_selection` 只读取订单并把候选和 selection_id 存入状态。
2. `await_order_selection` 调用 `interrupt`，负载是 JSON 可序列化的卡片数据。本节点中断之前不调用模型、不写退款、不重复写 SQL 用户消息。
3. 服务读取根检查点，确认是本轮的预期中断，发送选择事件和 `paused`，关闭本次 SSE、释放会话锁。此时没有 final_message_id，也不能发送假 `done`。
4. 用户点卡片后提交原 turn_id、selection_id、暂停 checkpoint_id、order_id。服务加同会话锁，核对最新根检查点仍是该暂停轮次，订单属于当时允许的候选，再以同一 thread_id 执行 `Command(resume=...)`。
5. 节点从中断处恢复后，单独的查单节点执行一次查单，再扩写、检索及回答。恢复沿用 SQL 用户消息身份，不新增一条“订单1001”用户消息，不重新做理解和分类。

暂停节点恢复时会从头重执行，因此读取准备、持久化身份和外部副作用与中断节点分离。不能用宽泛异常捕获吞掉 LangGraph 中断信号。

刷新页面从只读待办接口恢复卡片；服务重启从 SQLite 恢复原轮。请求中不能把旧 checkpoint_id 当成历史分叉执行目标；恢复前只用它与最新状态做比较，真正恢复读取当前线程，避免旧卡片重新播放已失效流程。

### 5.3 新消息、重复点击与断连

- 用户不选单而发新问题：在同一会话锁中标记旧待选轮被取代，再以普通输入字典开始新轮，不传 `Command(update=...)` 充当新消息。旧 selection_id 失效，返回 409；不影响以前已经完成的人工/工单建议。
- 两次并发点选：只有一次能获得执行权，另一次返回可识别的忙碌/冲突，不重复跑模型。已完成后的相同选单请求可根据本轮选单回执重放已保存的结果，不再次调用上游；不同订单或已被新轮取代则 409。
- 同一轮暂停期间不占用 240 秒执行时限；恢复重建运行期客户端和 monotonic deadline，但保留本轮已消耗的 token/工具计数。首次执行与恢复两个活动段合计最多 240 秒，不因反复恢复累加新预算；人等候时间另计。
- 恢复后服务失败或用户断连沿用取消和不完整答复规则，不能当成已完成退款判断。对于已经离开合法等待状态的请求，不提供盲目重放运行中的图入口，提示用户重新发起或查看已保存结果。

SQL 历史继续只回放完整轮次；被放弃的孤立用户消息有状态审计，但不喂成已完成答案。待选提示和卡片从检查点恢复展示，避免在 SQL 中间插入普通 assistant 消息而破坏现有成对工具历史。

## 6. 公开 HTTP / SSE 契约

普通 `POST /api/chat` 输入保持不变。动作入口沿用 JSON、同源写入检查、规范会话 ID、会话锁、统一错误投影；客户端不能提供用户身份或任意执行节点。

| 入口 | 数据与结果 |
| --- | --- |
| `GET /api/conversations/{id}/pending-order` | 返回当前 awaiting_order 的 turn_id、selection_id、暂停 checkpoint_id、卡片和提示；无待选返回 `pending:null` |
| `POST /api/conversations/{id}/actions/select-order` | 严格四字段：turn_id、selection_id、checkpoint_id、order_id；校验后以 SSE 恢复原轮 |
| `POST /api/conversations/{id}/actions/refund` | 严格字段：assistant_message_id、checkpoint_id、offer_id、reason；创建或返回同一待审核申请 |

恢复接口的 HTTP 错误在 SSE 启动前返回；已经开始流式执行后的错误沿现有 `error` 事件并终止，不夹杂第二份 HTTP 响应。

增加三个事件，旧事件名和旧 `actions` 两种选项不变：

- `order_selection`：turn_id、selection_id、checkpoint_id、提示和卡片；卡片只含展示与选择所需字段，金额使用整数分。
- `paused`：turn_id、selection_id、checkpoint_id、`reason=order_selection`，表示已持久化等待，前端解除发送忙碌态；此后流关闭。
- `refund_offer`：绑定已完成答复的 assistant_message_id、checkpoint_id、offer_id，及订单只读摘要、判断说明、固定原因列表。

`done` 仍只在 SQL 最终答复与根 completed 检查点都已保存后发送。`refund_offer` 与既有建议一样在持久化完成后发布，不能仅凭模型文本或未完成流显示提交权限。刷新后的聊天展示根据原完成检查点重建合法入口，不从 DOM 或答案关键词重建权限。

## 7. 退款判断、申请权限与 MySQL 记录

### 7.1 显式判断，不按正文关键词猜按钮

仅在订单优先子流程使用扩展版 Agent 控制 Schema：原有 `reply_mode/suggested_actions` 加上 `refund_decision` 与 `decision_reason`。普通路径继续使用第五步原协议。`refund_decision` 枚举为 `eligible/needs_review/ineligible/not_applicable`，理由为受限非空文本。

含义分别是已知条件支持申请、仍需人工核验、有证据明确不符合当前诉求、当前是维修等非退款办理。它们都不是退款审批结果。没有商品完好等必要事实时不能声称已经满足全部条件；超过无理由时限但可能适用质量保修时应区分，不统一判所有售后不合格。

只有有效意图为退款退货、订单有效、政策闸通过、reply_mode 为 answer、判断为 eligible 或 needs_review，才由服务器生成 offer_id 并将其与订单/政策/判断快照写入完成根检查点。售后意图强制 `not_applicable`；澄清轮、资料不足、错误轮及未完成轮都不能发退款表单入口。矛盾控制输出视为错误，不从回答文本推测修正。

最终答复说明已知条件及仍需核验的部分，退款必须待审核；不得生成“已经退款”、到账时间承诺或虚构审批结果。退款表单与建工单是两个入口，互不触发。

### 7.2 提交与幂等

客户端只传完成答复定位和原因；金额、状态、订单归属、政策、工具结果、是否可申请一律从服务器保存的快照恢复。接口核对根命名空间、完成状态、SQL 答复与会话归属、offer_id 以及用户消息关系，不相信客户端隐藏字段。

固定原因使用稳定代码与中文标签：`unwanted` 不想要了、`quality` 质量问题、`not_as_described` 与描述不符、`wrong_or_missing` 发错/漏发、`damaged` 运输破损、`other` 其他。本章不在对话中追问原因，也不在本表单请求银行卡或支付密码。全部原因初始不预选；服务端拒绝未知项。

`refund_requests` 存在现有 MySQL，字段为：

| 字段 | 设计 |
| --- | --- |
| id、request_no | BIGINT 主键、唯一对外申请号；申请号由服务器稳定身份派生 |
| conversation_id、user_message_id、assistant_message_id | 来源会话与本轮消息外键，保留追溯 |
| checkpoint_id、offer_id | 不可变完成快照定位；offer_id 唯一，阻止一份表单重复创建 |
| user_id、order_id | 服务器确定的演示身份和订单；索引 `(user_id, order_id, status)` |
| pending_key | 对规范用户/订单身份编码后取 SHA-256；唯一键，防止跨会话重复待审核申请 |
| reason | 上述固定原因枚举 |
| amount_cents、currency | 订单实付全额、CNY；本章不做部分退款及金额编辑 |
| status | 服务器默认“待审核”；本章无修改状态 API |
| order_snapshot、policy_snapshot、decision_snapshot | JSON，保留业务时间、事实版本、实际政策 chunk 全文/路径和判断；不是只保存当前库 ID |
| created_at | 服务端创建时间，与演示业务时间分开 |

申请在短事务中创建，不把网络或模型调用包进数据库事务。以现有 Conversation 行锁串行同会话写入，`pending_key` 唯一约束处理同用户同订单跨会话的竞争；不依赖进程锁覆盖跨会话情况。相同 offer 与相同原因返回原申请；相同 offer 改原因返回 409，不覆盖已经提交的内容。

同一用户同一订单已有待审核申请时，不论从哪一轮表单进入都不新增；同源 offer 可返回原结果，其他 offer 返回 409 并告知已有申请。不能只靠先查再插；唯一键冲突须退出失败事务，再用新 Session 读取并核对归属及幂等字段，其他完整性错误不得冒充重复成功。本章申请始终待审核，`pending_key` 不释放；后续若增加审核终态，再设计业务键释放与重新申请规则。

退款记录写入不改变 tickets、会话人工状态或订单状态，不调用支付接口。SQL 提交完成但响应丢失时，重复提交读取原申请号。SQLite 与 MySQL 不组成跨库事务：SQLite 完成快照提供申请依据，MySQL 唯一键保障申请写入幂等，不声称二者原子提交。

新增 SQL DDL 沿用 utf8mb4，与 SQLAlchemy 模型同步；不改已部署历史迁移，不在本设计阶段执行建表。

## 8. 前端呈现与用户交互

沿现有 MewHelp 原生 HTML/CSS/JavaScript 和主题对话框实现，不引入 UI 组件库，不使用浏览器黑色原生 confirm/prompt。

- 缺订单时，在聊天流展示“请选择要办理的订单”和可点卡片，含商品型号、订单号、状态、实付和演示时间说明；选中后锁定同组卡片并展示选择结果，恢复原问题的处理。
- 等待期间可继续发新问题；旧卡片显示已失效。刷新及重启可恢复尚合法的选择器，不能只在页面内存记 pending。
- 退款入口打开主题一致的表单：订单及金额只读，退款原因下拉必选，提交按钮显式提示“提交后待审核”。取消不请求后端，成功在聊天流另起结果气泡展示申请号及待审核，不把提交当作已退款。
- 转人工继续在聊天流显示独立接入通知和客服小猫新气泡；建工单仍由用户手填类别和描述。新增退款功能不回退已确认的这些交互。
- 卡片、原因、弹窗按钮可用键盘操作，提交中防双击；失败保留可编辑内容并显示服务端可操作错误，不能先显示成功再补报错。

前端按用户反馈直接迭代；不单设前端 brainstorm、TDD 或 code review 流程。跨端协议、后端校验及真实浏览器验收仍需覆盖，不以仅检查页面文本代替实际点击和数据验证。

## 9. 错误、预算与审计

模型原始输出非法、模型/向量库故障、数据不存在、等待用户、知识不足分别有独立结果。只对合法模型不确定输出使用“其他”；不把各类异常都变成固定拒答。

保留最终回答 512、理解/分类/扩写及 Agent 控制 JSON 2048 的输出上限，单次模型超时 60 秒、零模型重试、活动聊天总时限 240 秒、现有 FAQ 段 90 秒和最多四次逻辑工具调用。理解、分类、扩写各最多一次；恢复不重跑它们。新模型配置默认与当前上游相同，不自动降级或升级型号。

既有 32000 账本继续限制 Agent 决策/回答及分类成本；新增理解和扩写纳入同一账本并在调用前预留后续必要额度。内容充分性等既有检索内部模型调用另按阶段记账和时限限制，因此不能把此账本数字宣称为全链路严格 token/费用上限。每阶段真实 usage 优先、缺失用保守估算且标记 estimated，报表同时展示各阶段及总观测消耗。

节点日志记录：原轮 ID、理解是否改写、模型原始/有效意图、confidence、路由、暂停/恢复/取代、选单身份、查询数、各路候选和合并数、证据闸原因、Agent 步数及各阶段耗时/usage。可审计快照保存在受控业务记录及检查点；普通日志不输出完整工具数据、完整对话或密钥。不得展示或持久化模型思维链作为验收证据。

## 10. 验证与验收

### 10.1 Prompt 与标注集

建立固定 48 轮标注集：24 个单轮边界题、6 组每组四轮的会话，覆盖八类意图及物流→退款→物流切换、完整问题透传、多订单歧义、维修不变退款、纯 FAQ 不弹选单、未知问题归其他。逐轮标明先行词、期望规范问题、意图、是否选单/扩写、应获取的事实及允许的结果；先拆分开发样例与保留验收样例，再调 Prompt。

不以“字符串刚好相同”作为所有改写正确性的唯一判断：完整明确问题要求原样；需改写问题检查实体、诉求、否定和时间保持。结构协议另有离线坏输出样例，覆盖额外字段、低 confidence、截断、错误类型、伪造订单号和非有限数。

目标：48 轮意图至少 46 轮正确；标明完整透传的题全部不被改写；明确可消解的代词至少 95% 正确；歧义样例零猜单；关键退款/投诉/纯 FAQ 路由全部正确。JSON 可解析率与意图准确率分开计，错误不从分母剔除。受控模型只能验证接线，不能据此宣称真实 GLM 达标。

真实模型验证采用固定样例、有界执行：离线契约与图测试通过后，先运行保留集内固定 16 轮（四组四轮），每轮零重试，失败只定点复验；通过后才安排剩余标注样例验证。留存模型名、Prompt/样本版本、完成率、意图/指代指标、延迟和 usage；不自动扩成 300 题 RAG 评估或循环跑到通过。

### 10.2 后端功能验证

代码任务按 TDD 验证实际行为，Prompt/数据任务以标注集替代单测式 TDD。必要专项包括：

- 通用政策直接检索；具体退款/售后必定查单在前、政策在后，证据闸在最终生成前。
- 多查询逐条召回、跨路去重、统一重排一次、过滤一致、最终引用可回原文；错误不默默少一条查询。
- SQLite 真文件暂停、关闭并重新打开后恢复；SQL 当前用户消息只写一次，工具申请结果成对，预算不会恢复清零。
- 新消息使旧卡片失效；伪造候选/会话/历史检查点被拒；并发选择不重复执行。
- 退款必须有合法完成 offer；取消不写库、双击不重复、改原因冲突、跨轮/跨会话同订单待审核唯一、写成功响应丢失可安全重试。
- MySQL 故障不显示申请成功；mock 事实仍明确标注；旧完成检查点及工单动作可用。

### 10.3 真实浏览器验收

在隔离端口 8003 验收，保留现有 8002。使用 Computer Use；若其仍不可用，沿用已获允许的本机真实 Chromium 自动化替代，保存截图和可核对的后端日志/数据库结果。

| 场景 | 必须看见的结果 |
| --- | --- |
| “退换货政策是怎样的” | 强制 RAG、引用可点，没有订单选择器 |
| 查订单1001物流 → “它能退吗” → “那物流现在到哪了” | 意图切换与指代正确；退款先查单/政策；后续仍可正常查物流 |
| 新会话“这个能退吗” | 不猜商品/订单，出现卡片；点选后继续原轮而非重新提问 |
| 等待选单时刷新、重启 | 同一待选状态可恢复；新问题后旧卡片不可执行 |
| 退款判断后打开表单、取消、再提交固定原因 | 取消零记录；提交一次 MySQL 待审核，另起成功气泡 |
| 再次点击、跨会话同一演示用户同一订单申请 | 不产生第二份待审核记录 |
| “饮水机不出水要维修” | 订单后检索故障/保修/寄修，不出现退款表单 |
| “我要投诉”、问候和怪问题 | 各走固定出口；人工和工单继续独立，主题弹窗正常 |

浏览器端通过不代表真实支付或生产鉴权已实现。交付同时提供运行命令、测试结果、标注验证结果、数据库验收证据和 `dev-notes/ch06.md`；具体实施任务和命令在设计获批后的实施计划中列出。

## 12. 书面设计自审与后续门槛

自审已核对：纯 FAQ 与具体办理的路由一致；分类协议恰为两个字段且共八类；扩写为真正多查询；缺订单不猜；暂停不是完成、恢复不重复用户消息；退款仅用户提交后待审核；售后不自动变退款；历史工单及当前端口不受本设计阶段影响；模型及技术栈不变。
