# 第五步提示词：Workflow 确定性编排与主力 Agent

本文整理本次开发中用户提供的原始提示词，并单列后续明确确认的选项和验收纠偏。后续确认以最后一次用户要求为准，原始提示词不据此倒改。

## 使用插件

- Superpowers
- Context7

## 完整原始提示词

```markdown
现在先进行第五步开发吧，我要用 Superpowers 模式把客服系统升级成生产级架构:Workflow 确定性编排做骨架,主力 Agent 作为骨架里的核心节点。

## 功能需求
1. 祛魅热身:先不用框架,手写一遍最裸的 Agent 循环(调 LLM,有工具调用就执行并把结果喂回去,没有就收敛出答案),看清它就是个带工具的循环,再用 LangGraph 重构
2. 图骨架按这条流程搭:指代消解、意图识别、按意图分流、知识检索、置信度闸、主力 Agent、日志记录
3. 分流规则写死在代码里,把第 6 点的七类意图逐一归到四个出口:
   - 知识类(商品咨询、退款退货):强制先做 RAG 检索(复用第三步/第四步的检索器),检索完先过第 7 点的置信度闸,证据够才把检索结果连同问题交给主力 Agent;退款退货先检索政策再交给 Agent,Agent 仍可自己调订单工具
   - 业务数据类(物流、订单、售后):不预检索,直接进主力 Agent 让它自己调工具
   - 投诉:不进 Agent,回一句安抚话术,并按第 8 点把「转人工」「建工单」两个选项交用户自己选(两者是两回事,分开给),不后端自动执行
   - 闲聊:直接返回固定话术,不花模型调用
4. 主力 Agent 用 ReAct 循环:简单问题一次工具调用就收敛,复杂问题按中间结果多走几步,缺信息就追问用户;要有停止条件和 token 消耗控制。Agent 的工具复用第二步的查订单、查物流等 Function Calling 工具,本步骤不新写业务工具
5. 会话状态用 LangGraph 的 State 一路贯穿,持久化用自带的 checkpointer
6. 两个节点本步骤先放最简实现,后面再做正式版:指代消解先原样透传;意图识别用一个简单 prompt 判成物流、订单、商品咨询、退款退货、售后、投诉、闲聊七类,输出 JSON
7. 置信度闸本步骤先做到:卡在知识类检索之后、进 Agent 之前,Agent 的答复是流式吐给用户的,答完再判就晚了;证据弱就直接回兜底话术、不进 Agent,同时把这个问题记下来留给后面数据飞轮;业务数据类没有检索证据,不走这道闸(证据强弱可用第四步的证据覆盖度 / 检索得分做个阈值判断,先做最简版,正式的置信度检查留给可观测那一步)
8. 转人工、建工单是两件事,分开做,都交用户在前端自选、不后端自动执行:分流判成投诉、或 Agent 判断合适时,后端不直接动作,只在回复里带上建议的可选项(转人工、建工单,可只给一个也可两个都给);前端各渲染成一个独立按钮 —— 点「转人工」前端直接展示「已转接人工客服」,再蹦一句「您好,我是客服小猫,请问有什么可以帮您的」(本步骤就是前端模拟这个效果,不接真人系统);点「建工单」才调第二步的工单工具写 tickets 表;两个按钮互不绑定,用户哪个都不点、继续发消息,就当普通对话正常走下去

## 技术栈
- LangGraph:图编排 + State + checkpointer
- 前端:原生 HTML + CSS + JavaScript 聊天页,只在上面加「转人工」「建工单」两个按钮 + 确认交互

## 本步骤不做
- 意图识别和指代消解的正式版(下一步的事)
- 上下文管理策略升级、MCP 接入、飞轮入库(都留给后面)

## 验收标准
1. 问政策类问题,日志里能看到强制检索节点被走到
2. 问「订单 1001 的物流到哪了」,Agent 自己调工具作答
3. 说「我要投诉」,前端出现「转人工」「建工单」两个独立按钮;点「转人工」前端显示「已转接人工客服」并蹦出客服小猫的问候,点「建工单」才写 tickets 表,两者分开,都不点就接着正常对话、不做任何动作
4. 闲聊拿到固定话术
5. 一个要先查订单再查物流的复杂问题,能看到 ReAct 走了不止一步

## 工作要求
1. 全程走 Superpowers 流程,技能自动触发;产出不是可单测代码的任务(纯 Prompt、数据类),把 TDD 那步换成拿标注样例或评估集跑一遍验证,其余步骤照走
2. 过程留痕:在仓库 dev-notes/ch05.md 里追记开发过程,每完成一个阶段(brainstorm 定稿、计划评审通过、每个任务完成、code review 结论、finish)就补一段,记四样:我这一步发的关键原话、你的关键产出(spec / plan 路径、评审结论)、我拒绝或纠偏了什么、翻车与返工;不许收尾时一次性补记
3. 涉及具体库、框架、API 的用法(FastAPI、SQLAlchemy、LangChain、LangGraph、Milvus、Langfuse 这些),一律先用 Context7 MCP 查最新官方文档和接口定义再动手,别凭记忆写,版本对不上的 API 是返工重灾区
4. 上面点名的技术选型是定死的,实现中发现矛盾或走不通,停下来问我,不要自行换方案
5. 完结交付:功能演示命令、测试结果、dev-notes 路径
```

## 后续明确确认的方案

1. 闲聊边界：用户选择“明确闲聊规则直出，其余模型分类”。“你好、谢谢、再见”等明确整句闲聊使用规则，整轮不调用模型；其余问题通过模型分类。
2. 编排方向：用户批准“外层 Workflow 固定分流＋内部 Agent 循环子图”，同步改造多步历史回放与工具徽章。
3. 检查点存储：用户先提出必须使用 MySQL，随后在选项截图中改选官方 `AsyncSqliteSaver`。最终用独立 SQLite 文件保存 LangGraph 检查点，既有 MySQL 保存业务数据，不引入 PostgreSQL。
4. 文档查询：Context7 曾因审批服务 403 无法执行，用户明确允许当次使用 LangGraph／LangChain 官方文档继续，并留存来源；能正常使用 Context7 时仍先查询 Context7。
5. 设计与计划：用户分别批准设计文档和九项实施计划，选择 Subagent-Driven 实现；先用 8002 验证，保留原 8001。
6. 获批的基础限制：Agent 最多四次工具调用，累计预算 32000，控制 JSON 输出上限 2048，最终回答上限 512；具体用量口径与限制见设计及裁决记录。
7. 真实模型验收：用户明确允许使用项目 `.env` 当前同一 GLM 接口，完成固定聊天场景及失败样例修复后的定点复验；每轮 240 秒、零重试、模型和预算不变，不运行 300 题评估。

## 用户验收过程中的交互纠偏

用户原话：

> 这里应该转人工应该在聊天框显示已接入人工，然后直接另起一个新气泡回复，而不是直接在原来的气泡追加，工单也要自己填

随后再次明确：

> 不对啊，而且会弹出黑框，太丑了，搞一个适配主题的弹窗

最终交互要求：

- 转人工使用与聊天页一致的浅绿圆角确认弹窗。取消、关闭或 Escape 均不执行接入。
- 确认后，在消息列表新增“已接入人工客服”通知，再新增客服小猫的独立问候气泡，不把文字追加在原回答内。
- 建工单打开空白表单，用户自行选择类别并填写描述；只有提交才调用原工单工具写库，取消不写。
- 两个按钮状态独立；只转人工不建单，只建单不转人工，两者都不点则继续普通聊天。
- 转人工仍为前端演示，不连接真人系统。
- 前端沿用此前用户明确要求的 Vibe Coding 例外，以实际页面效果和浏览器验收为准。
