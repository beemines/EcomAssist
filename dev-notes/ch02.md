# 第二步开发过程：工具调用与数据库持久化

## 2026-10-06 — 需求接收与设计前核对，尚未定稿

### 用户关键原话

- “我要用 Superpowers 模式给现有的客服系统装上查数据的能力,用 Function Calling 让模型自己决定调什么工具——工具链要长在客服聊天本身,用户在聊天页问一句就能触发。”
- “FastAPI 加 SQLAlchemy 的分层骨架;Docker 起 MySQL;建四张表灌测试数据”。
- “只做单轮调用:模型调一次工具就收敛”。
- “换个说法问『邮费是多少』,确认关键词查表查不出来——这个漏召回是预期结果,记下来留给下一步升级”。
- “聊天页改造是例外,用 Vibe Coding 方式直接做”。

### 关键产出

- 本次包含数据库、工具执行和 SSE 协议扩展，按 Superpowers brainstorming 的架构设计路径推进；正式 spec、实现计划和业务实现均尚未开始。
- 检查 master 上现有入口、模型工厂、内存历史、流式响应、客服 Prompt 及聊天页面。明确保留 `/api/chat`，新增状态帧时修正终止事件判定，工具申请与结果按完整轮次回放和裁剪。
- 实际调用 Context7 查询 LangChain 工具定义/工具调用、SQLAlchemy 异步 MySQL/事务/LIKE、FastAPI 流式依赖生命周期与 Docker Compose；在现有锁定环境核对 `bind_tools`、`@tool` 和 `ToolMessage` 的接口。
- 研究结果保存到 `docs/superpowers/research/2026-10-06-tool-calling-apis.md`。
- 提出单轮数量澄清：“每条用户消息最多执行一个工具”还是“一次选择多个工具后统一收敛”。当前待回复，推荐前者。
- 拟采用短数据库事务、完整工具调用消息组与工单防重复写入策略；保持四张业务表，不建立订单、商品和物流表，不加入 Agent Loop 或 RAG。

### 用户拒绝或纠偏

- 当前无新增回答或设计批准。沿用用户既定技术栈及此前的中文注释、UTF-8 和开发步骤表述，不擅自替换方案。
- 本阶段仅核对事实与整理设计；用户对第一步的批准不作为对第二步尚未展示的 spec/计划的批准。

### 翻车与返工

- Docker CLI 可用，但 Docker Desktop Linux Engine 未运行，命令返回 Server 为 null 和管道不存在；未启动容器、清空数据或替换数据库。
- Context7 的首轮综合查询混入其他模型适配器的参考条目，随后改查 ChatOpenAI 参考并核对已安装接口。
- 智谱文档索引未匹配到当前模型的具体工具调用说明，补充官方域名搜索也未定位；仅记录资料缺口，不据此判定兼容失败，不自动改模型。真实请求次数为 0。

## 2026-10-06 — brainstorm 定稿，保存用户 DDL 与正式 spec

### 用户关键原话

- “确认，然后以上是建表语句，到时候执行这段来建表，然后放一个sql文件在代码中进行存放”。
- 用户给出 conversations、messages、faq、tickets 的完整 MySQL DDL，明确数字自增会话主键、中文枚举、工具申请 JSON、tool_call_id 及两个外键。

### 关键产出

- 用户已批准上一轮聊天中展示的单轮工具调用设计；执行方式沿用已有 Subagent-Driven，前端继续按 Vibe Coding 例外处理。
- SQL 原样保存到 `sql/schema.sql`，保留用户提供的字段、默认值、索引、外键、存储引擎、字符集与原始注释。建表阶段通过 MySQL 原生 SQL 执行，不让 SQLAlchemy 重新生成替代 DDL。
- 正式 spec 保存到 `docs/superpowers/specs/2026-10-06-tool-calling-design.md`，覆盖 Docker 建表/种子、ORM 分层、五个工具、单轮与有限重试、SSE、持久化、裁剪及验收；尚待用户审阅，未提前编写实现计划。
- 根据数字主键设计新增会话创建接口、聊天使用 conversation_id；根据固定表结构设计完整轮次回放与基于工单主键的重试防重复，不新增数据库列。
- spec 明确数据库提交后再 done 的完成边界，以及独立的可配置工具输入预算；这些变更在正式文档中公开供用户审阅。
- 完成 spec 自审：未发现占位符、选型矛盾、额外业务表或 Agent Loop/RAG 越界；核对调用数量、取消、FAQ 漏召回与数据库边界的一致性。
- 验证 SQL 表名/顺序、四处 InnoDB/utf8mb4、两个外键及关键字段/枚举；文档链接、围栏和 UTF-8 无 BOM 检查通过。SQL 尚未执行，不将文本校验当作 MySQL 集成验收。

### 用户拒绝或纠偏

- 用户指定建表语句作为权威结构，替代自行生成表结构的做法；原 DDL 中没有会话 UUID、轮次状态或工单幂等键，不擅自补列。
- 同次工具执行的重试使用稳定工单主键防重复；不将其描述为用户重发消息的跨请求去重。

### 翻车与返工

- 发现旧聊天 UUID 与用户的 BIGINT 主键不一致；在写 spec 时对齐为数据库 conversation_id，页面和演示命令将在实现中一起调整。
- 固定 DDL 没有轮次完成状态列，设计改为通过已验证的完整消息组合识别可回放轮次，保留未完成的真实流水而不将其作为模型历史。
- 无数据库执行或产品代码返工；本阶段仅保存用户 SQL、正式设计与研究/过程记录，真实模型请求次数仍为 0。
