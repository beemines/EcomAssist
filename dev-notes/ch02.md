## 2026-10-06 — 需求接收与设计前核对，尚未定稿

### 用户关键原话

- “我要用 Superpowers 模式给现有的客服系统装上查数据的能力,用 Function Calling 让模型自己决定调什么工具——工具链要长在客服聊天本身,用户在聊天页问一句就能触发。”

### 关键产出

- 检查 master 上现有入口、模型工厂、内存历史、流式响应、客服 Prompt 及聊天页面。明确保留 `/api/chat`，新增状态帧时修正终止事件判定，工具申请与结果按完整轮次回放和裁剪。
- 实际调用 Context7 查询 LangChain 工具定义/工具调用、SQLAlchemy 异步 MySQL/事务/LIKE、FastAPI 流式依赖生命周期与 Docker Compose；在现有锁定环境核对 `bind_tools`、`@tool` 和 `ToolMessage` 的接口。
- 研究结果保存到 `docs/superpowers/research/2026-10-06-tool-calling-apis.md`。
- 提出单轮数量澄清：“每条用户消息最多执行一个工具”还是“一次选择多个工具后统一收敛”。当前待回复，推荐前者。
- 拟采用短数据库事务、完整工具调用消息组与工单防重复写入策略；保持四张业务表，不建立订单、商品和物流表，不加入 Agent Loop 或 RAG。

- 正式 spec 保存到 `docs/superpowers/specs/2026-10-06-tool-calling-design.md`，覆盖 Docker 建表/种子、ORM 分层、五个工具、单轮与有限重试、SSE、持久化、裁剪及验收；尚待用户审阅，未提前编写实现计划。

### 用户拒绝或纠偏

- 用户指定建表语句作为权威结构，替代自行生成表结构的做法；原 DDL 中没有会话 UUID、轮次状态或工单幂等键，不擅自补列。
- 同次工具执行的重试使用稳定工单主键防重复；不将其描述为用户重发消息的跨请求去重。

### 翻车与返工

- 发现旧聊天 UUID 与用户的 BIGINT 主键不一致；在写 spec 时对齐为数据库 conversation_id，页面和演示命令将在实现中一起调整。
